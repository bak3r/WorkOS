# The Algorithm 8.45.0

## The point

The target of every run is **euphoric surprise** (system prompt § The One Loop): the principal got exactly the desired output, in the right amount of time, for the right amount of spend.

**Direction comes first** (§ The One Loop), because every passing criterion makes a build of the wrong thing look like success. The run checks the ISA's `## Ideal State` ladder (ISAFormat) before building, when a correction arrives, and before claiming done. When the work and the ladder disagree, stop climbing and resolve it.

This file states what must be true for done. How I get there and how much I spend is my judgment. I don't declare an effort tier or predict difficulty up front. The output format is the system prompt's contract, separate from this one.

## Route (the entry step)

Routing is my judgment against `AlgorithmReference.md` § Routing, the one home of the system's rules about who runs what, at what effort and how wide; read it before choosing a lane, an effort or a width. WorkOS runs Claude only, on Amazon Bedrock, so every lane is a Claude rung.

**Depth is native.** The principal's depth words ("think deeply", "go heavy", "quick pass") are an explicit ask (criterion 10), and Claude Code's own effort and thinking carry the depth. Which thinking skills, agents and rungs serve it is my call (§ Spend); no step is prescribed and nothing skipped owes a line.

## The Loop

The loop and the ISA as the hill and the test suite are stated once in `WORKOS/WORKOS_SYSTEM_PROMPT.md` § The One Loop. A criterion's Test Strategy rows are its checks, run in cost order: a code assert or direct probe when the criterion is literal, a judged row (`eval`, `pairwise` or `glance`, ISAFormat) through the Assay skill (`skills/Assay/Tools/EvalRunner.ts`) when it needs reading, the principal only for taste. A criterion's asserts run before its judges, and a failing assert settles it.

Read `WORKOS/ALGORITHM/AlgorithmReference.md` § Loop background when explaining, documenting or changing the Algorithm's purpose or lifecycle; if relevance is uncertain, read that section before acting.

## A run is complete when

Teeth: **HOOK** blocks mechanically · **CHECK** is a gate the run executes and records · **SELF** is honest self-attestation.

1. **The work points at the right ideal state, checked before building.** The principal's goal is verbatim in `principal_stated_goal` (immutable unless they revise it). The ISA opens with the `## Ideal State` ladder: L3 always, L2 on project, system and feature-bearing ISAs, L1 on project and system ISAs. The literal is a pointer; its intent is the target, and every criterion traces to the ladder or a named derived criterion. On a new project or a changed direction the principal saw L3 and L2 before building (`Skill("ISA","restate")`), and `bun WORKOS/TOOLS/IsaLadder.ts drift <isa>` ran once before close, with any `partial` or `divergent` verdict resolved. *(CHECK: `IsaLadder.ts check` and `drift`)*

2. **Done existed in writing before building.** Non-trivial work has its criteria in an ISA before the first artifact exists; a trivial change in a repo with no ISA needs none. Inside a project with an ISA, size exempts nothing: code sync binds every change (its one home is the system prompt § The Algorithm; mechanics ISASystem.md § Code sync). A task ISA lives at `WORKOS/MEMORY/WORK/{slug}/ISA.md`. The ISA of a repo that is not yours to put files in (an employer repo) lives there too and names the repo with a `repo:` frontmatter link, never written into that repo; a repo of your own may carry its own `ISA.md`, which then governs it. Every criterion names its falsifier and carries at least one Test Strategy row (`manual` when nothing executable exists yet, never no row). Done is extracted, never transcribed: on new-product work the ISA articulates the ideal state from everything knowable, every candidate is dispositioned in the extraction manifest (criterion, fog, out-of-scope, killed), and the run closes a milestone while the ISA holds the whole hill (`milestone_progress`; `phase: complete` means the ideal state itself). Mechanics: ISA Scaffold and ISAFormat § Extraction. Substantial or persistent builds run `Skill("ISA","check completeness")`; a trivial task may write a minimal L3, criteria and Test Strategy ISA directly. *(HOOK: `IsaCodeSyncGate` blocks a turn that changed governed code without writing its ISA · SELF: the governing ISA is read before the first edit and is current before anything ships; WorkOS has no start check and no release gate)*

3. **What must not happen is written down:** at least one anti-criterion. On a new project or an ISA with several Features, a fresh mind that never saw the criteria runs an absence review, and each finding becomes an `absence` row in the manifest; skipping it costs a Decisions row. *(CHECK · advisory ISAGate `no-anti-claim`)*

4. When the goal is experiential, at least one antecedent names what reliably produces the feeling. *(CHECK)*

5. External prerequisites (tokens, logins, service config, deploy targets) were probed before execution. MISSING blocked or was ratified deferred in the Log; UNKNOWN surfaced but never blocked. Gotcha: a credential that authenticates can still lack the scope, so probe each one with a read-only call that exercises the exact scope the work needs; an install's fuller runbook in OPERATIONAL_RULES wins. *(SELF)*

6. **Material ambiguity was resolved before building, and Discuss keeps the ladder aligned through the climb.** Name where the ideal state lives first. Discoverable from the record (code, repo, prior ISA, deploy state): read it, with up to 3 targeted questions, an inline ambiguity flag when a default is safe, and a whole-response `proceed` accepting the defaults; a named but unverified referent ("the ticket", "what we discussed") is found on record or asked about before the artifact exists. Exemplar-anchored new-product work: run the extraction pass and have the principal ratify the forks, batched. Only in their head: `Skill("ISA","discuss <topic>")` in `discover` mode before Scaffold writes more than the ladder. **Through the climb, a Discuss round is owed before the uncertain part is built** whenever `bun WORKOS/TOOLS/IsaAlign.ts status <isa>` says DISCUSS, a restate answer is more than a clean yes or a wording fix, drift says `partial` or `divergent`, or a correction changes the destination (ISAFormat § The alignment loop). `quick` is one round, and unblocked criteria keep climbing. A single local decision stays an `ask` under its criterion (`Skill("ISA","refine")`). `proceed` or "just build it" overrides, logged in Decisions. *(CHECK: `IsaAlign.ts status`)*

7. A reported bug was reproduced before its suspect code was read, and the fix moved upstream when one fix kills the class. **When the same test or error survives two fixes, the next move is a fresh diagnosis, never a third patch:** a non-forked Opus-rung agent that never saw the attempts reads the code and the failure cold (§ Telemetry, second looks), or one Log line names the new evidence that makes the next fix different. *(SELF · Log bypass for pure-additive work, non-isolable symptoms, or repros that would cause damage)*

8. **No criterion closed without tool evidence of the right modality:** file→Read, code→Grep, command→checked output, HTTP→`curl -i`, deploy→live probe, web/UI→real browser via Interceptor when one is available (headless sandbox: tests + HTTP-level evidence, labeled as not-a-browser-check; visual claims stay DEFERRED), appearance→viewed pixels, motion→frame scrub, schema→SELECT, config→read-back, behavioral, quality or regression→eval pass^k. A judged criterion needs a judged row (`glance`, `eval` or `pairwise`). A run that executes a skill intent whose skill ships an eval suite names that suite as its verification (`skills/Assay/Tools/EvalRunner.ts`), and it cannot close with the suite unrun or a code check failing. Evidence spans the criterion (a container passing proves nothing about its members) and arrives when the failure can exist (`WORKOS/RULES/Verification.md`). "Should work" is forbidden. The evidence is mine to gather: a criterion is never closed, deferred or handed over by asking the principal to screenshot, test, look at or confirm anything a tool here can check (tests, probes, the Assay skill, and Interceptor with `VerifyViewport.ts` wherever a browser is available) (principal directive, 2026-10-25; system prompt § The Climb). `[DEFERRED-VERIFY]` names its follow-up task and blocks complete unless waived in the Log. *(HOOK: VerificationGate)*

9. **A defect that is one instance of a class closed only after one grep enumerated every sibling**, each fixed and verified, or tombstoned: `🧹 CLASS-SWEEP: <class> — N siblings via <probe>; M fixed, K tombstoned`. Sweep-shaped asks (rename, retire, bump, migrate) enumerate at plan time across both trees (`~/.claude` and the USER target). Changing a file other things read is changing an API: grep its consumers and run their tests as part of the change. *(CHECK)*

10. Every explicit ask in the principal's message was met, skipped with a stated reason, or surfaced. Scope narrowed only where they ratified it, and no criterion passed because its wording softened mid-run. Depth and steering words are explicit asks. One line goes to `MEMORY/OBSERVABILITY/ask-fidelity.jsonl`; any ✗ blocks complete. *(CHECK: last gate before learn)*

11. **Validation is intrinsic and the builder never grades its own build.** A forked subagent counts as the builder, so an independent look runs non-forked. A second look (a non-forked Opus-rung review that never saw the build, or an eval suite) is elected by blast radius or on request, never required for correctness; it stays in the Anthropic family and is labeled a same-vendor second look. For core-surface, security or publish-bound work, electing no independent look at all costs one Log row naming why. Review contradictions are surfaced, never silently resolved: two re-calls, then escalate to the principal. Every finding is dispositioned in the Log: adopted (diff), rebutted (reason) or deferred (task). *(CHECK)*

12. **The run left its trail, and the ISA keeps only what stays useful.** Git is the changelog; the ISA has no changelog section. It keeps decisions, dead ends, and what changed in understanding. When a criterion closes, its evidence collapses to a one-line stub (commit, test name, probe). Learnings land through the Learning Router (default skip; knowledge→KNOWLEDGE, incident→`MEMORY/LEARNING/INCIDENTS/`, preference or rule→OPERATIONAL_RULES (never CLAUDE.md, which only routes), gotcha→the skill, state→PROJECTS.md, work→`WORK/`; identity, doctrine, hook and permission changes go to the principal). Changed system files trigger the documentation-sync skill, if the install has one. *(CHECK)*

13. The ISA frontmatter stayed current: `phase:` set at start, `complete` at close, changed in between only when it really changed, and `progress:` true. *(ISASync mirrors every ISA write to work.json)*

14. The ISA at close is not the ISA at open: corrections, failed probes and discovered constraints were folded in as they arrived, adding, splitting, tightening or killing criteria; answered asks were folded, open ones settled `default-unratified` (`IsaAsks.ts settle`). *(SELF · falsifier: discoveries in the transcript with no ISA deltas)*

15. **The spend and the time matched the task**, scaled to the difficulty and blast radius the work revealed; the principal's explicit calls outranked everything; breaks in either direction were surfaced. An ask that is not major work reached a usable result in minutes; a run past about ten minutes stated its ETA up front and delivered a usable slice first. Blast radius is the reach of the answer, never the shape of the deliverable: advice that would steer doctrine or a persistent ISA is doctrine-grade work even as three paragraphs. *(SELF)*

16. **Previous functionality was restored or improved, proven against a baseline.** When the run replaced, rerouted or deleted anything serving live traffic or a flowing metric, a baseline was captured first and parity closed on the flow's rate after the change, never on one synthetic event. Destructive ops enumerate ownership through the provider's API before and after, and safety mitigations become criteria before the op runs. Mechanics: `WORKOS/RULES/Verification.md` rule 6. *(CHECK · HOOK: AlgorithmNudge destructive-infra row)*

## Spend

Intelligence, verification depth, parallelism, time and money follow the difficulty and blast radius the work reveals, never a predicted label. The principal's plain-language call ("go heavy", "quick pass", a budget) outranks my judgment, and a depth call binds the route.

**Reach prices the spend.** A chat-shaped answer that would change doctrine, a standing rule, a persistent ISA, or how future runs behave enters the loop and earns the scrutiny that change would earn. "It's just analysis" is never by itself a reason to stay conversational, and prose about something inert stays cheap however long the prompt.

**Execution shape is mine.** `AlgorithmReference.md` § Routing holds the width tiers, counted in separable parts.

**Who runs what is `AlgorithmReference.md` § Routing,** the one system home for lanes, rungs and agents; the principal's own rung doctrine in OPERATIONAL_RULES § Model selection outranks it where the two differ. The carrier is configured in `settings.json` and a run never changes it. Which rung the core takes is my call; legs go down the work ladder per § Routing.

**Thinking skills are the default when the work matches their shape:** Council for debate, RedTeam for adversarial attack, IterativeDepth for multi-lens passes, ApertureOscillation for scope tension, FirstPrinciples for constraint teardown, SystemsThinking for recurring structure, RootCauseAnalysis for incidents, BeCreative for divergent ideas. Review agents critique; they never substitute for the skill.

Four facts are not judgment calls:

- **Inline-reachable answers spend nothing.** If I can answer from what's in front of me, zero agents. Every writing agent's output is probed on disk before I trust it. Fan-outs past about 8 agents reserve verification budget and name a non-agent fallback in the Log.
- **Work units fit the smart zone (about 100k tokens).** Close a coherent unit and re-enter fresh from the ISA rather than push through compaction. Scoping that must stay whole runs in one window; execution slices each get a clean one. When fog exceeds one window, the ISA's frontier carries it across sessions.
- **Model IDs live only in `WORKOS/TOOLS/models.ts`;** § Routing names rungs by alias. A dispatch that omits `model` inherits the session model, which is what "best available model" means; the `max` rung resolves through `EFFORT_MODEL` there, to Fable where the provider offers it and to Opus where it does not.
- **A delegate that goes idle gets one nudge, then is reported FAILED, its absence named in the output.** No criterion closes on a report that never arrived. Size briefs so one silent death loses little; a fan-out that needs babysitting belongs in the Workflow tool, which owns deadlines and retries.

## Telemetry & records (tool contracts)

- **Phase:** write `phase:` at start (`marking` while articulating, `climbing` once building), at `complete`, and between only on a real change. Every other run state is derived by `deriveAscent()` in `WORKOS/TOOLS/ascent.ts`; never hand-list state names, and never compute the phase strip yourself: `hooks/ISASync.hook.ts` injects a `<workos-ascent-delta>` block on each derived-state change, and I echo it verbatim once per transition.
- **Reflection** (any run that did real work): `bun WORKOS/TOOLS/Reflect.ts --session <id> --slug <slug> --reflection "<what a smarter run would have done>"`, all three flags required.
- **Fan-out:** orchestration is mine, never the principal's. When agents or a Workflow carry the work, the main session stays the ISA's only writer: delegates hand results back and the main session ticks criteria from their evidence.
- **Resume:** an ISA body edit on a `phase: complete` task rewinds to `learn`, `iteration+1`. After compaction, read the ISA and continue; never redo passed gates.
- **Second looks:** dispatch non-forked with the ISA and the stated goal restated verbatim: `Agent(subagent_type:"Max")` (read-only; Fable where offered, Opus on Bedrock) or any non-forked dispatch with `model: "opus"`. No agent reviews work it built. Unreachable means skipped for cause, never blocked.
- **When a run may stop:** only when every open criterion is closed or blocked on something only the principal can give (a decision, credential, account, go-ahead). A blocked criterion never pauses the unblocked ones. Before closing, name each open criterion's blocker; any criterion without one means the turn continues.
