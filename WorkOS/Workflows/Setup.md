# Setup — system integration (phase 1)

Wires WorkOS into the user's work environment. Runs FIRST, always — hooks and integration must land before the Interview seeds anything. One continuous UX; this is the "logistics" half, the Interview is the "meaning" half.

## Sandbox (sbx) notes

The target is a Docker Sandboxes (sbx) Linux microVM with deny-all egress. That changes a few things:

- **Config root = `$CLAUDE_CONFIG_DIR`** (the sandbox sets it to `<workspace>/.claude`, symlinked into `~/.claude`). `DetectEnv` reports it as `configRoot`; pass that value to every tool as `--config-root` and never assume `~/.claude`.
- **USER data home:** `ScaffoldUser`/`LinkUser` default to `~/.config/WORKOS`. If that path is not persisted across sandbox rebuilds, set `WORKOS_CONFIG_DIR` to a persisted location outside the config root (e.g. `<workspace>/.config/WORKOS`) before steps 5–6.
- **Install offline.** There is no route to GitHub, so bootstrap from a local release directory: `WORKOS_SRC=/path/to/release bash install/install.sh` skips every network fetch.
- **Dependencies:** `DeployCore` runs `bun install` for the config root and each nested `package.json`. With deny-all egress that fails unless the npm registry is allowlisted or `node_modules` ships pre-installed in the release directory; report the failure plainly rather than retrying.
- **Required sbx kits:** the `bun` kit (every install tool runs under bun) and the `claude-home-link` kit (links the workspace config root into `~/.claude`). Without either, stop and say which one is missing.
- There is no systemd user session guaranteed, no GUI and no audio, so the background-service components in step 7 are normally declined.
- **Launch from the project, with `-l`.** The `workos` launcher (`WORKOS/TOOLS/workos.ts`) `cd`s into the config root (`$CLAUDE_CONFIG_DIR`, i.e. `<workspace>/.claude`) before starting Claude unless it is given `-l`/`--local`; it takes no project-directory argument (a bare path is rejected as an unknown command). So in sbx, `cd` into the project and run `workos -l` — plain `workos` starts the session in `.claude`, not the code. `-l` refuses a repo's main checkout when the repo uses `.claude/worktrees` (override: `WORKOS_ALLOW_ROOT=1`), and the one-shot `workos prompt "<text>"` always runs from the config root.
- **Constitution in the sbx TUI.** The TUI starts plain `claude`, so the launcher's `--append-system-prompt-file` never runs there. `DetectEnv` reports `sandbox: true` when the config root is not `$HOME/.claude`; then recommend (never auto-apply) the opt-in at step 8: `ActivateImports.ts --with-system-prompt` @-imports `WORKOS/WORKOS_SYSTEM_PROMPT.md` from `CLAUDE.md`, so every plain `claude` session gets it as context. `workos` sees the active import and stops appending its own copy, so it never loads twice. Undo with `--without-system-prompt`.
- **npm packages are usually absent** (see Dependencies above). The affected tools say "unavailable" and exit 1; `Doctor.ts` shows which as `npm-deps`. Details: `GETTING-STARTED.md` "Optional npm dependencies".
- **Bedrock / Vertex:** with `CLAUDE_CODE_USE_BEDROCK=1` (or Vertex) and an `availableModels` list that has no Fable id, the `max` rung resolves to `opus` (`WORKOS/TOOLS/models.ts`) and `agents/Max.md` installs with `model: opus`.
- **bun ≥ 1.2.21** — hooks and tools parse YAML with Bun's built-in `Bun.YAML`, added in 1.2.21; an older bun kit fails every hook at import. `Doctor.ts` reports it as the `bun` capability.

## Two-tier model

Deployment is **two tiers**, and the install presents them that way:

- **WorkOS Core** (steps 4–6, 8, 8.5) — system prompt + base settings + `CLAUDE.md`/identity, the skills library and the WORKOS runtime (Algorithm, documentation, tools, statusline, version, user-templates) deployed by `DeployCore` (step 4.5), **and the `workos` launch command that actually loads the system prompt** (step 8.5). This IS WorkOS; it installs as one bundle after a single consent ("install WorkOS Core?"). Declining means not installing WorkOS at all.
- **Enhancements** (step 7) — hooks, statusline, tool tips, spinner verbs, agents, background jobs. À la carte: the user (or their AI, from context) picks some, all, or none. Each is independently deployable, idempotent, and reversible.

The skill ships everything for both tiers in its payload; nothing activates without the matching consent.

## Steps

0. **Inventory and adopt** — before anything is written.
   - `bun Tools/InstallRun.ts start` opens the install run (one `.workos-backup/<run>/`, one set of manifest lines; the bootstrap `install.sh` starts it for you when it ran first).
   - `bun Tools/Inventory.ts` (READ-ONLY) classifies the config root: claude-owned / lifeos-copy / lifeos-edited / lifeos-data / workos / user / collision, plus the `settings.json` and `CLAUDE.md` summaries. **Show it to the user and ask before going on.**
   - If LifeOS is present (`DetectEnv` → `existingInstall.lifeos`, or Inventory lists `lifeos-copy` / `lifeos-data`): `bun Tools/Adopt.ts` (dry run), then `--apply` on a yes. Untouched LifeOS copies move to the backup, `LIFEOS/MEMORY/*` except `STATE/` is copied into `WORKOS/MEMORY/`, LifeOS hook registrations / statusLine / default `LIFEOS_*` env leave `settings.json`, and `LIFEOS/` moves to the backup. Edited and own paths are kept and listed; WorkOS does not install over them.
   - Then the normal steps below.
1. **DetectEnv** — `bun Tools/DetectEnv.ts` → `{os, harness, display, ssh, bun, existingInstall: {workos, lifeos}, isDevTree, settingsExists, claudeMdExists, configRoot}`. An explicit `CLAUDE_CONFIG_DIR` is always honored as `configRoot`. Thin entry point over the sibling `Tools/InstallEngine.ts` (`detectEnv()`) — a reshaped, bare-skill subset of the legacy installer engine.
   - **If `isDevTree` → STOP.** Never mutate the author's source repo. Print the refusal and exit.
2. **ScanConflicts** (read-only) — `bun Tools/ScanConflicts.ts` → existing settings hooks, skill-name collisions (skill dirs only), LifeOS presence and every Inventory collision, existing populated config tree. Produces the branch decision for `LinkUser`.
3. **Prereqs** — confirm `bun` present and ≥ 1.2.21 (`bun --version`; `Bun.YAML` is used by hooks); confirm harness is one of the supported set; surface any missing prerequisite as a plain-language fix, do not auto-install system packages.
   - **If `harness.confidence` is `"assumed"`, confirm the harness with the user before branching** — detection was a guess (config dir without the harness binary, or the clean-machine default), and a leftover `~/.claude` dir must not send a non-Claude-Code install down the Claude Code path (hooks + `workos` alias both require the `claude` CLI). Ask which harness is actually running this setup, and branch on the answer.
### — WorkOS Core (steps 4–6, 8; one consent) —

4. **System overlay** — place the harness-root system files (each `existsSync`-guarded — never clobber a populated harness):
   - `install/CLAUDE.template.md` → `CLAUDE.md` (the routing table; its identity `@`-imports ship dormant as `# @WORKOS/USER/...` and are activated later by `ActivateImports`). `DeployCore` (step 4.5) places it when no `CLAUDE.md` exists yet and never touches an existing one — an existing one gets a marked WorkOS block at step 8, its text kept.
   - `install/WORKOS/WORKOS_SYSTEM_PROMPT.md` → the system prompt. This is the real, public-clean system prompt shipped in the payload — used directly, no separate template.
   - **settings → `bun Tools/InstallSettings.ts`** (dry-run first, then `--apply`): places `install/settings.system.json` → `settings.json` (the system half — WITHOUT hooks; `InstallHooks` owns hooks). Over an existing file it unions `permissions` allow/deny/ask, adds only absent env and other keys, never adds or changes `model` / `availableModels` / `theme` / plugin keys, and lists `securityRelevantSettingsToAdd` in the dry run — show that list before `--apply`. The tool expands `$HOME`/`~` in `env` values at write time — the harness injects env values verbatim (#1404/#1451), so a hand copy ships literal `$HOME/...` strings that create a real `$HOME/` junk directory at runtime. Never copy this file by hand.
   - Substitute the identity/version placeholders — `{{PRINCIPAL_NAME}}`, `{{PRINCIPAL_FULL_NAME}}`, `{{DA_NAME}}`, `{{DA_FULL_NAME}}`, `{{WORKOS_VERSION}}` (the full set `checkSurvivingPlaceholders` checks) — in the files placed by THIS step: `bun Tools/Substitute.ts --root <configRoot>/settings.json --principal-name <name> --da-name <name> [--principal-full-name <n>] [--da-full-name <n>] --apply` (full names default to the short names; the version defaults to `<configRoot>/WORKOS/VERSION`, so pass `--version` before 4.5 has placed it). Note the scope: skills and the WORKOS runtime don't exist yet — they land in 4.5 — so this pass cannot reach them. The full-tree pass and its verification are step 9(d), and that is what makes the install identity-correct.
4.5. **Deploy core system: skills + runtime** — `bun Tools/DeployCore.ts` (dry-run first, then `--apply`): copyMissing's the shipped `install/skills/` → `<configRoot>/skills/` (the ~50-skill library) and `install/WORKOS/` → `<configRoot>/WORKOS/` (the runtime — ALGORITHM, DOCUMENTATION, TOOLS, statusline, VERSION, USER_TEMPLATES), EXCLUDING `USER` (step 5 scaffolds it) and `WORKOS_INSTALL`; an existing skill dir that isn't WorkOS's is never written into (`keptYours`), and an existing `node_modules/` is never touched; the empty `MEMORY/` tree (WORK/KNOWLEDGE/LEARNING/STATE/OBSERVABILITY/SKILLS) is scaffolded here too so the runtime has a home to write to. Targets ALL-CAPS `WORKOS` so the `@WORKOS/...` imports resolve. Never overwrites a populated file (idempotent), refuses the dev tree (`isDevTree` → exit 2), and FAILS LOUD (exit 1) if a required payload source is absent — never a silent no-op. **Runs BEFORE ScaffoldUser**: the active `@WORKOS/DOCUMENTATION/ARCHITECTURE_SUMMARY.md` import must resolve and the skills must exist before the rest of setup.
5. **ScaffoldUser** — `bun Tools/ScaffoldUser.ts` (dry-run first, then `--apply`) → `existsSync`-guarded copyMissing from the shipped `install/USER/` template tree into the user config tree. Never overwrites a populated file.
6. **LinkUser** — `bun Tools/LinkUser.ts` (dry-run first, then `--apply`) → relocate/symlink the config tree into the harness tree (3-branch logic ported from the install engine; EXDEV fallback; throw on symlink failure). Config root keeps its canonical name.
### — Enhancements (step 7; à la carte, some/all/none) —

7. **Enhancements menu** — present the optional components; let the user (or their AI, from context) pick any subset. Two deployers back this, both `isDevTree`-refusing, idempotent, backup-before-write:

   | Component | What it deploys | Default |
   |-----------|-----------------|---------|
   | `hooks` | Algorithm nudges, memory, context injection — most features need these | **recommended** |
   | `statusline` | `WORKOS_StatusLine.sh` + `settings.json` `statusLine` (an existing non-WorkOS statusLine is kept unless `--replace-statusline`) | optional |
   | `tooltips` | `settings.json` `spinnerTipsOverride` — 265 WorkOS Claude-Code tips, shipped public-clean in `install/settings.enhancements.json` | optional |
   | `spinnerverbs` | `settings.json` `spinnerVerbs` — 523 custom spinner verbs, shipped in `install/settings.enhancements.json` | optional |
   | `agents` | the shipped `agents/` tree (copyMissing, never overwrites; on Bedrock/Vertex without Fable in `availableModels`, `Max.md` installs with `model: opus`) | optional |
   | `worksweep` / `derivedsync` / `commitmentsweep` | background jobs (`systemd --user` on Linux) | optional — decline in sbx unless a user systemd session exists; with `hooks` installed, WorkSweep and CommitmentSweep already run from the `MaintenanceJobs` hook |

   - **hooks → `bun Tools/InstallHooks.ts --apply`** (trust-gated; without `--apply` it only prints the plan): reads `install/hooks/hooks.json`, shows the EXACT change (file + settings-entry + event count), waits for explicit permission, backs up `settings.json`, merges additively per matcher bucket (idempotent via normalized-command dedup, preserves `type:"http"` verbatim). It STOPS, writing nothing, when a same-named file under `hooks/` is not WorkOS's — run Adopt (LifeOS copies) or rename the file.
   - **everything else → `bun Tools/DeployComponents.ts`**: dry-run first (no `--apply`, `--all` shows the full plan), then `--apply --components <csv>` with ONLY what the user picked. Reads enhancement settings from `install/settings.enhancements.json` (the keys split out of `settings.system.json` so they're genuinely opt-in, not force-bundled). A component whose prerequisite is absent reports a LOUD blocker and fails — never a silent no-op. Background jobs need a `systemd --user` session; if `systemctl --user` is unavailable (the usual sbx case), skip them.
   - **Verify (two evidence classes)** per applied component: statusline/tooltips/spinnerverbs → re-read `settings.json` shows the key set; agents → files present under `agents/`; background jobs → `systemctl --user is-enabled com.workos.<name>.timer` succeeds.
8. **ActivateImports** — `bun Tools/ActivateImports.ts` (dry-run first, then `--apply`) → uncomment the identity `@`-imports in `CLAUDE.md`, each guarded by `existsSync` of the symlink-resolved target. When `CLAUDE.md` is the user's (not placed by DeployCore), it inserts `<!-- WORKOS:BEGIN -->…<!-- WORKOS:END -->` at the top instead and keeps their text; `--fix-lifeos-paths` rewrites their `LIFEOS/` paths to existing `WORKOS/` ones. The dry run prints the unified diff — show it before `--apply`. Path literals stay as the canonical `@`-import form. The system-prompt import is never activated by this pass; add `--with-system-prompt` only when the user accepts the sandbox route (recommended when `DetectEnv` says `sandbox: true`).
8.5. **Wire the launch command (Core)** — the constitutional system prompt placed in step 4 (`WORKOS_SYSTEM_PROMPT.md`) only loads when the harness is launched with it appended; a plain `claude` session never sees it. Wire a `workos` launch command per `INSTALL.md` step 7 — **Claude Code:** a permission-gated `workos` alias in the user's shell rc (`alias workos='bun <configRoot>/WORKOS/TOOLS/workos.ts -s <configRoot>/WORKOS/WORKOS_SYSTEM_PROMPT.md'`), shown exactly, rc backed up first, idempotent (never double-add); **other harnesses:** their own system-prompt flag against the same file. If the user declines the shell edit, hand them the one-line launch command to run by hand. In a sandbox that took the step-8 `--with-system-prompt` opt-in, the launcher is still useful (banner, MCP profiles) but no longer the only route to the constitution. **Without this, WorkOS Core is installed but launches un-constituted** (plain `claude`, no mode banner / verification / security layer).
9. **Verify (three evidence classes)** — (a) the config tree resolves (the identity `@`-imports load) — ALWAYS checked, it's Core; (b) IF the user opted into `hooks`, a probe session shows the mode banner / context injection fire. If hooks were declined, skip (b) and surface the caveat plainly: the constitutional mode banner and the memory loop are hook-enforced, so without hooks WorkOS Core installs but runs un-bannered and un-augmented — recommend hooks unless there's a reason to decline; (c) the **launch command is wired** — grep the shell rc for the `workos` alias (or confirm the user was handed the manual one-line launch). Without it, Core installed but launches un-constituted — say so plainly. Report what was checked; never claim a hooks-fire pass when hooks weren't installed. (d) **No identity placeholder survives.** Everything is on disk now, so run the substitution pass the step-4 pass could not reach, over the whole deployed tree: `bun Tools/Substitute.ts --principal-name <name> --da-name <name> [--principal-full-name <n>] [--da-full-name <n>] --apply` (default root `<configRoot>`). It renders all five tokens — `{{PRINCIPAL_NAME}}`, `{{PRINCIPAL_FULL_NAME}}`, `{{DA_NAME}}`, `{{DA_FULL_NAME}}`, `{{WORKOS_VERSION}}` — then runs `checkSurvivingPlaceholders` over the same roots and exits 0 only when `surviving` is 0 (run it without `--apply` first to see the sites). On a raw 7.15.0 payload that is 303 tokens across 104 files, so a skipped or mis-rooted pass is the difference between a system that knows the user's name and one that addresses them as `{{PRINCIPAL_NAME}}`. Non-zero survivors means substitution didn't take: re-run it against the reported paths, and if they persist, say so plainly rather than proceeding to the Interview. Two scope limits, both deliberate, both stated so the check is not read as broader than it is: it covers the identity/version tokens only — the payload legitimately carries other `{{TOKEN}}` forms (Art's thumbnail templating, Fabric pattern bodies) and flagging those would train the installer to ignore the gate — and it walks the template extensions, skipping `MEMORY/` (user data, never templatized). Substitution and verification share one traversal, so anything the checker cannot see is also something substitution never reached.
10. **Transition** — `bun Tools/InstallRun.ts finish`, then print: "Setup complete. Now let's set WorkOS up for your work —" and roll into `Workflows/Interview.md`.
11. **Rollback (if the user wants it undone)** — `bun Tools/Rollback.ts` (dry run), then `--apply`: replays `WORKOS/install-manifest.jsonl` in reverse and restores the root byte-identical to before the run (LifeOS files and `LIFEOS/` come back from `.workos-backup/<run>/`). Run it from outside the config root — it removes `skills/WorkOS`.
