# PruneComments

Reduces the comments a branch or commit added to the ones that tell a reader something the code cannot, edits comments only, and proves with a code-stripped comparison that no code changed. The result is an uncommitted working-tree change the user reviews.

## Ideal State

- Every comment the change added that restates code, narrates steps, logs history or comments out code is gone or shortened; every why-comment, warning, directive and required doc comment remains.
- `CommentScan.ts verify` exits 0: no code changed, only comment text.
- The report lets the user spot a wrong cut fast: every removal with its file, line and reason.

## Intent Routing

| Intent | Trigger | File |
|--------|---------|------|
| **PruneComments** | "reduce comments on this branch", "clean up comments in commit X", "remove useless comments", "just show which comments you'd cut" | `Intents/PruneComments.md` |

**Tool:** `Tools/CommentScan.ts`, built for C# first. `scan` lists comment blocks added by a branch (vs its merge-base) or one commit, tagged `comment` / `doc` / `inline` / `directive` / `looks-like-code`, skipping generated files. For C# it also tags XML doc blocks (`echoes-name`, `echoes:param(x)`, `empty:returns`, `inheritdoc`, `public-api` / `non-public`, `docs-required-by-build`, `may-feed-openapi`) and prints each owning project's doc policy from its `.csproj`, `Directory.Build.props` and `.editorconfig`. `verify` compares every changed file before and after with comments stripped, and fails if any code changed. Read-only git.

## Data & Config

Optional `PREFERENCES.md` at `<configRoot>/WORKOS/USER/CUSTOMIZATIONS/SKILLS/PruneComments/` (`configRoot` is `$CLAUDE_CONFIG_DIR`, else `~/.claude`): stricter or looser keep rules, doc-comment policy per repo.

## Gotchas

- **Only comments the range added are in scope.** Pre-existing comments in the same file are not this change's to judge, however bad. The scan output is the boundary.
- **Some comments are functional.** Linter/compiler directives (`// eslint-disable`, `#pragma`, `// ReSharper disable`, `# type: ignore`, `//go:build`), shebangs, license headers and `<auto-generated>` markers change behaviour. The scan tags them `directive`; never remove them.
- **C# doc comments can be load-bearing.** With `GenerateDocumentationFile` plus warnings-as-errors, removing `///` from a public member fails the build (CS1591): the scan tags these `docs-required-by-build`. In a web project the XML doc file usually feeds Swagger/OpenAPI (Swashbuckle `IncludeXmlComments`, NSwag, .NET 9+ OpenApi): tagged `may-feed-openapi`, so an echo summary there is still the API's published description. A DTO in a class library can feed OpenAPI too when the web project includes that library's XML file; the tag cannot see that, so check before cutting DTO docs.
- **`/// <inheritdoc/>` is functional.** It pulls the interface's or base class's docs into IntelliSense and the XML file. Keep it.
- **Lines inside C# strings are not comments.** `//` or `/* */` inside a raw `"""` string (SQL, JSON) or a verbatim `@"..."` string is data. The scanner knows this; do not "fix" what it did not list.
- **`// language=json`, `// ReSharper disable`, `// <copyright>` and `// csharpier-ignore` are tool directives.** Tagged `directive`; keep them. `// Arrange` / `// Act` / `// Assert` are tagged `test-marker`: a test convention, keep them.
- **Python and JS docs matter too, outside C#.** Python docstrings become CLI help in Click/Typer and endpoint descriptions in FastAPI; JSDoc carries types under `checkJs`.
- **Generated files are skipped on purpose.** Hand edits to `.g.cs`, `.Designer.cs`, migration snapshots or generated clients vanish on the next regeneration.
- **A merge commit as `--commit` pulls in the whole merged branch.** Its first-parent diff is other people's work. Use branch mode, or a non-merge commit.
- **For an older commit, line numbers drift.** The scan says "approximate — locate by text" when HEAD is not the scanned tip; find each comment by its exact text in the current file, and skip ones tagged `GONE-from-working-tree`.
- **Verify needs a clean start.** If the tree was dirty before pruning, `verify` cannot tell the prune from the earlier edits.

## Examples

**Example 1: current branch**
```
User: "reduce the comments on this branch"
→ CommentScan.ts scan (current branch, base auto-picked)
→ removes or shortens low-value comments in the working tree
→ CommentScan.ts verify passes
→ reports what was cut and why, leaves the change uncommitted
```

**Example 2: one commit, preview only**
```
User: "which comments from a1b2c3d would you remove? don't change anything"
→ CommentScan.ts scan --commit a1b2c3d
→ returns the proposed cuts, no edits
```
